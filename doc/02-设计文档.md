# FriesTrader 设计文档

## 1. 设计目标

FriesTrader 设计为一个双阶段交易管线，其目标是将：

- 候选发现与 thesis 写作
- 风控计算与下单门槛
- 审计日志与状态持久化

完全分离开来。

该设计的本质是：

- AI 仅用于筛选与解释
- 规则脚本负责决策判定
- 人类负责最终是否确认为 live trading

## 2. 设计原则

1. 分层设计
   - 数据接入层
   - 风控/规则层
   - 决策执行层
   - 日志/状态层

2. 硬规则优先
   - risk_rules.json 作为唯一真相源
   - 模型不能覆盖数值规则

3. 可审计优先
   - 所有决定都要写入 trade_log.jsonl
   - 每次执行都要带 reason / stage / action

4. fail-safe 优先
   - 缺数据、失败、异常都要停止可能危险动作

5. dry-run 先行
   - live trading 必须经过人工确认和足够周期验证

## 3. 总体架构

FriesTrader 基本可分为四层：

### 3.1 数据接入层

数据接入层通过 Robinhood MCP 获取：

- watchlist 列表
- watchlist 项目
- quote 数据
- historical 数据
- fundamentals
- positions
- portfolio value
- earnings data
- pnl history
- order review / order placement

### 3.2 配置层

配置层的核心文件是：

- risk_rules.json

它定义了：

- account_number
- execution.mode
- universe 过滤参数
- signal thresholds
- position sizing
- stop loss / take profit
- wash sale
- earnings blackout
- sell re-entry lock
- loss limit

### 3.3 决策执行层

核心脚本：

- entry_gate.py：决定是否允许买入 / 加仓
- stop_loss.py：决定是否触发止损
- take_profit.py：决定是否触发止盈分档卖出
- conviction_trim.py：决定是否裁减持仓
- rank_candidates.py：按优先级排序候选
- position_sizing.py：按资金和仓位有限度分配交易数量
- pnl_pct.py：判断是否触发 loss limit halt

这些脚本全部采用 JSON 输出，方便 Pipeline 直接读取而不是重算。

### 3.4 状态与报告层

状态层包括：

- pending_proposals.jsonl：当天候选与 thesis
- trade_log.jsonl：事件日志，append-only
- trade_log_recent.md：每日 readable summary

## 4. Phase 分工

### 4.1 Phase A：筛选 + Thesis

输入：

- risk_rules.json
- Robinhood watchlist
- supplementary scan

输出：

- screened 记录
- thesis 记录
- summary buckets

Phase A 的职责：

- 过滤候选池
- 计算 signal
- 确定是否进行 news search
- 生成 direction / conviction / thesis / risk_flags / sources
- 写入 pending_proposals.jsonl

它不做交易，也不能.place order。

### 4.2 Phase B：复核 + 风控 + 下单 + 日志

Phase B 的工作流：

1. 读取 pending_proposals.jsonl
2. 读取 trade_log.jsonl
3. 识别 held/new/exit_existing candidates
4. 处理 sell-side 风险
5. 重新读取 portfolio 和 positions
6. 执行 entry_gate
7. rank candidates
8. position sizing
9. 进行 live/dry_run gate
10. 执行 review_equity_order 和条件判断
11. 最终记录 order 和 risk_check
12. 生成 cycle_summary

## 5. 关键组件设计

### 5.1 entry_gate.py

职责：

- 检查 entry price gap
- 检查价格是否相对 moving average 过度延伸
- 检查 wash sale
- 检查 sell re-entry lock
- 检查 earnings blackout

输出：

- passed
- blocking_conditions
- action

## 5.2 stop_loss.py

职责：

- 根据 average cost 与 current price 计算 drawdown
- 在 fixed 或 volatility_scaled 模式下得到 stop_pct_used
- 根据 trailing high 或 average cost 计算参考价格
- 判定是否触发止损

输出：

- stop_reference_price
- stop_reference_basis
- drawdown_pct
- stop_pct_used
- triggered

### 5.3 take_profit.py

职责：

- 对每个 tier 计算当前 gain_pct
- 处理多档同时触发时的 cascade logic
- 输出 fired_this_cycle 与 final action

### 5.4 conviction_trim.py

职责：

- 判断是否 overweight
- 结合 consecutive low/medium conviction cycles
- 在满足条件时触发 partial sell

### 5.5 rank_candidates.py

职责：

- 对候选按 conviction 排序
- 在同一 tier 内按 risk_flags 数量排序
- 再按 pct_below_52wk_high 排序

排序原则：

1. high > medium > low
2. risk_flags 越少越靠前
3. pct_below_52wk_high 越大越靠前

### 5.6 position_sizing.py

职责：

- 计算每个候选要买多少
- 计算 cash_remaining 和 concurrent positions
- 遵守 max_position_pct_of_account 和 cash buffer
- 处理 top-up 的最小金额门槛

输出：

- results
- cash_remaining_final
- concurrent_positions_after_final

### 5.7 pnl_pct.py

职责：

- 计算日度 / 周度 realized P&L 占 net deposits 的比例
- 判断是否达到 loss limit
- 如果达到阈值，设立 entries_halted

## 6. 数据流设计

### 6.1 Phase A 数据流

Robinhood 数据 -> universe filter -> signal detection -> news research -> thesis -> pending_proposals.jsonl

### 6.2 Phase B 数据流

pending_proposals.jsonl -> candidate classification -> sell-side risk checks -> portfolio refresh -> buy-side checks -> ranking -> sizing -> order review -> execution -> logging

## 7. 状态管理设计

### 7.1 pending_proposals.jsonl

这个文件只保存当前周期候选，是 Phase A 产物，Phase B 读取它。

### 7.2 trade_log.jsonl

这个文件是事实日志的根源，内容包括：

- thesis
- risk_check
- stop_loss
- take_profit
- conviction_trim
- loss_limit_check
- order
- cycle_summary

它必须是 append-only。

### 7.3 trade_log_recent.md

它是人类可读的总结视图，不是机器事实来源。

如果 trade_log.jsonl 与 trade_log_recent.md 发生冲突，优先相信 trade_log.jsonl。

## 8. 安全设计

### 8.1 dry_run to live gate

系统要求：

- live mode 必须手工开启
- dry_run 至少需要达到指定 cycle 数
- live-order gate 需要 review_equity_order 通过

### 8.2 fail-safe 设计

当以下条件发生时：

- API 失败
- 脚本失败
- 数据不完整
- 数值异常

系统应该：

- 标记失败
- 拦截该候选
- 记录日志
- 不做主观补算

### 8.3 幂等设计

Phase B 使用 proposal_date 作为每个候选的幂等键，避免：

- 同一 thesis 因日期不同被重复处理
- stale proposal 被重复买入

## 9. 关键工程决策

### 9.1 规则脚本优先

FriesTrader 设计中，AI 不再直接手工计算：

- 不做 stop % 计算
- 不做 gap % 计算
- 不做小数分配
- 不做 rank 和 sizing 的手工排序

所有这些都交给脚本；上下游只需要读取 JSON 输出。

### 9.2 读日志而不是靠记忆

系统设计强调：

- 任何决定都要留下证据
- 运行时读新鲜状态，不缓存旧值
- 不依赖“上次看起来差不多”

### 9.3 状态在 repo 中，而不是本地文件系统

项目设计明确要求：

- pending_proposals.jsonl
- trade_log.jsonl
- trade_log_recent.md

都保存在 git repo 中，因此可以通过 cloud routine、git push 和 remote 状态持续跟踪。

## 10. 结论

FriesTrader 的架构核心是：

- AI 负责研究与判断
- 确定性脚本负责执行门槛
- repo 负责状态持久化
- 审计日志负责追根溯源

这种结构使它更接近“规则受控自动化交易系统”，而非纯粹 “LLM 自己发号施令” 的交易代理。
