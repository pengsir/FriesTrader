# FriesTrader 需求文档

## 1. 项目概述

FriesTrader 是一个面向 Robinhood 的自动化 AI 交易管线，核心目标是把“AI 选股与推理”与“风险执行与订单控制”分离开来。
 
它的设计思路不是让模型直接决定是否买卖，而是把关键的风控逻辑固化为脚本和规则，使模型只能负责：

- 发现候选标的
- 做研究与写 thesis
- 提交建议

真正的执行决策由 deterministic scripts 负责，例如：

- stop_loss.py
- take_profit.py
- entry_gate.py
- position_sizing.py
- pnl_pct.py
- rank_candidates.py
- conviction_trim.py

## 2. 业务目标

FriesTrader 的目标是：

- 让 AI 在有限范围内完成股票筛选和基本研究
- 让机械规则决定是否允许交易
- 为每次决策保留审计日志
- 在人工显式允许下，才允许 live order 执行

换句话说：

- AI 负责“为什么值得研究”
- 规则脚本负责“是否允许下单”
- 人负责“是否真的用真实资金”

## 3. 业务场景

这个项目适用于：

- 个人/小型投资账户
- 需要自动化每日候选筛选
- 需要在一天中的固定时点做审视和执行
- 希望把 AI 交易过程从“黑盒决策”改为“可审计流程”

## 4. 系统角色

### 4.1 人类操作者

人类操作者负责：

- 配置 Robinhood 账户和 watchlist
- 维护 risk_rules.json
- 评估 dry-run 结果
- 在确认稳定后手工切换 execution.mode 为 live
- 检查 trade_log.jsonl 与 trade_log_recent.md

### 4.2 AI 执行器

AI 执行器负责：

- 在 Phase A 中筛选标的并生成 thesis
- 在 Phase B 中根据 risk rules 进行再验证与决策
- 面对风控脚本输出时遵照规则执行，不做自由发挥

### 4.3 Robinhood MCP

Robinhood MCP 是系统的数据源和执行接口，提供：

- watchlists
- quotes
- historials
- fundamentals
- positions
- portfolio value
- earnings data
- order review
- order placement

## 5. 核心功能需求

### 5.1 Phase A：筛选与 thesis

Phase A 必须：

- 读取最新的 risk_rules.json
- 合并 watchlist + 扫描器候选
- 过滤掉不符合 universe 规则的标的
- 确保当前持有头寸始终被纳入候选池
- 使用最新的 quotes 和 historials 计算信号
- 奖励高质量 signal，但限定 news search 预算
- 生成 thesis 行
- 将结果写入 pending_proposals.jsonl

Phase A 仅做筛选与分析，不负责下单；所有 order 工具都被硬性限制。

### 5.2 Phase B：复核、风控、执行与日志

Phase B 必须：

- 读取 pending_proposals.jsonl
- 读取 trade_log.jsonl 进行去重和状态验证
- 按照候选类型进行分类：new / held / exit_existing / avoid
- 执行 sell-side 风控：
  - stop loss
  - take profit
  - conviction trim
  - exit_existing
- 执行 buy-side 风控：
  - entry_gate
  - loss-limit check
  - sell re-entry lock
  - wash-sale check
  - earnings blackout
- 对候选按 conviction / risk_flags / pct_below_52wk_high 排序
- 通过 position_sizing 计算出每个候选的资金规模
- 按 dry_run / live 设置决定是否真的执行订单
- 记录所有决策到 trade_log.jsonl
- 补充生成 trade_log_recent.md

## 6. 风控要求

系统的硬规则包括：

- execution.mode 必须由人类显式控制
- 如果 execution.mode == dry_run，AI 不能发真实订单
- risk_rules.json 是不可覆盖的“硬约束”
- 模型必须遵守规则脚本输出，而不是人工重算
- 如果脚本失败或数据缺失，必须 fail-safe
- 任何违反规则的交易必须在下单前被拦截

## 7. 非功能需求

### 7.1 可审计性
所有关键操作都必须写入日志，且应可追溯：

- symbol
- date
- timestamp
- proposal_date
- stage
- reason
- action
- script 输出字段

### 7.2 确定性
该系统强调 deterministic decision：

- 相同输入 => 相同规则输出
- 不允许模型凭 narrative override 规则

### 7.3 安全性
系统必须避免：

- duplicate scheduled runs
- stale proposal loop
- live execution in wrong mode
- destructive git recovery in the middle of an active cycle
- guesswork when data is missing

### 7.4 追踪和恢复
对每趟交易都必须保留日志、候选、状态，以便后续回溯问题来源。

## 8. 关键约束

- 不能让 AI 自动修改 execution.mode
- 不能在 dry_run 下发真实订单
- 不能把“好故事”覆盖“止损规则”
- 不能对缺失数据进行自行假设
- 不能在 live 运行中尝试使用不安全的 git 重置或强制 push

## 9. 业务接受标准

项目成功的核心标准是：

1. Phase A 只做筛股和 thesis，不下单
2. Phase B 读取新鲜状态并按规则执行
3. 风控脚本返回可直接消费的 JSON
4. trade_log.jsonl 是 append-only 的事实记录
5. dry_run 能稳定运行且可审查
6. 人类在确认后手动切换 live 模式
7. 没有任何未审计的真实订单发出

## 10. 总结

FriesTrader 的核心价值不在于“模型看起来很聪明”，而在于：

- AI 负责筛选与推理
- deterministic scripts 负责计算与执行门槛
- logs 负责记账与审计
- 人负责最终是否投入真实资金

这个结构使系统更接近“受控自动化交易”而非“黑盒 AI 盲投”。
